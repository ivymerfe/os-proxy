Многопоточный HTTP-proxy, версия HTTP 1.1.
Язык C++, Все по классам, ссылки и умные указатели.
Сборка через cmake.
исходники в папке src
Без дополнительных библиотек кроме pico http parser
pico http parser в папке lib/parser: lib/parser/picohttpparser.h, lib/parser/picohttpparser.c
Архитектура прокси в виде mermaid диаграммы с md документацией
Все ошибки стандартных функций должны быть корректно обработаны (!)
Не должно быть холостых циклов, sleep, usleep и тп.
Допускается использование стандартных примитивов синхронизации pthread, системных вызовов select и poll и вызовов асинхронного ввода-вывода.

Должен быть реализован модуль логирования, чтобы можно было писать сообщения с разными уровнями важности (ERROR, WARN, NOTICE, LOG, DEBUG) было понятно, что происходит.
Все возникшие ошибки должны параллельно фиксироваться в модуле логирования с уровнем ERROR или WARN, содержать описательный текст и идентификатор проблемного сокета и URL.

Бинарник прокси должен принимать CLI флаги для удобства запуска и конфигурации (подходит getopt из стандартной библиотеки или getopt_long). Обязательно необходимо реализовать поддержку следующих флагов\*:
--port - порт, на котором слушает прокси. По умолчанию 8080
--max-client-threads - максимальное кол-во работающих
потоков (размер пула клиентских подключений).
По умолчанию 4.
--help - вывод сообщения о том как запускать прокси,
возможных флагах и их описания
--cache-initial-size - начальный размер кэша (в байтах, а также через суффиксы K/M/G, например 1M). По умолчанию 1Мб
--cache-max-size - максимальный размер кэша (в байтах, а также через суффиксы K/M/G, например 1M). По умолчанию 10Мб
--cache-ttl - время жизни кэш записи. По умолчанию 5с.

- В случае с использованием getopt допускается сокращение название флагов до -p, -t и -h соответственно

# Требования к реализации

Прокси должен принимать соединения на 8080 порту и возвращать данные из кэша.

В случае если для запроса нет записей в кэше, то должен быть создан отдельный поток, который загрузит в кэш требуемые данные.
Данные должны пересылаться клиенту как только они начали появляться в кэше.

Допускается реализация только через thread-pool.
Реализация должна уметь поддерживать больше сессий, чем есть потоков в пуле.

Прокси должен корректно информировать как клиента, так и сервер об используемой версии протокола.
Корректная обработка GET, PUT, POST, DELETE

Прокси-сервер должен корректно перехватывать все внештатные ситуации и при невозможности успешно обслужить запрос возвращать клиенту валидный HTTP-ответ с соответствующим статусом и текстовым пояснением в теле ответа (Content-Type: text/plain или text/html).

Обязательна реализация следующих HTTP-кодов:

- 400 Bad Request — синтаксическая ошибка при парсинге HTTP-запроса от клиента (некорректный формат стартовой строки, битые заголовки или превышение максимального размера заголовков (16 КБ)).
- 500 Internal Server Error — внутренние сбои в работе прокси-сервера (ошибка выделения памяти, сбой создания потока/примитива синхронизации, системные ошибки I/O).
- 502 Bad Gateway — сетевые сбои при взаимодействии с целевым сервером:
  1. Не удалось разрешить DNS-имя целевого сервера (getaddrinfo).
  2. Отказ в установке TCP-соединения со стороны целевого сервера (Connection Refused).
  3. Неожиданный разрыв соединения целевым сервером до получения полного ответа.
  4. Целевой сервер вернул некорректный/невалидный HTTP-ответ.

- 504 Gateway Timeout — превышение допустимого таймаута (10 секунд) на установку соединения, чтение или запись данных при обмене с целевым сервером.

- Поддержка любых механизмов авторизации на сайтах не обязательна.
- Редиректы: прокси не следует редиректам сам. Ответ с кодом, начинающимся на 3, и заголовком Location должен транслироваться клиенту без изменений: решение, куда переходить, принимает клиент.

Не должно происходить одинаковых запросов по URL одновременно. Т.е. если несколько клиентов одновременно идут по одному адресу (работают с одной записью кэша), то должен быть совершен только один веб запрос на сервер. Остальные клиенты должны ждать появления данных в кэше и при появлении части данных возвращать их клиенту. Нельзя ждать пока вся запись появиться в кэше.

Прокси должен корректно обрабатывать сброс клиентских сессий. В том числе, в случае, когда две или более сессий работали с одной записью кэша, после сброса одной из них, остальные сессии должны корректно продолжить докачку ресурса. А не начинать заново.

# Требования к кешу

- Кэш должен работать как мапа URL -> content. Входит ли query string URL в ключ кэша решать вам, но выбор должен быть задокументирован.
- Кэшировать нужно только ответы с кодами HTTP 200. Все остальные ответы передавать без изменений и не кэшировать (Методы PUT, POST и DELETE кэшировать не нужно).
- Кэшировать нужно все ресурсы (как текстовые, так и бинарные). Обязательно сохранение MIME метки ресурса.
- Кэш хранится в оперативной памяти и может полностью теряться при перезапуске прокси. Персистентный кэш будет плюсом.
- Кэш должен инвалидироваться (иметь TTL). Спустя некоторое время (по умолчанию, 5 секунд) с момента как все данные попали в кэш они должны считаться инвалидированными. При запросе по инвалидированному URL нужно будет выполнять веб запрос заново.
- Кэш должен уметь продолжать работать после заполнения текущего максимума. Нужно или аллоцировать на лету еще один сегмент (когда размер кэша еще не достиг максимума), или реализовать логику для удаления ненужные записи. Для определения ненужных записей нужно реализовать алгоритм, например, LRU, SLRU, LFU, Clock и тп. В любом случае, аллокация или GC должны быть в отдельном потоке, и не должны мешать работе прокси.
- Ресурс, превышающий максимальный размер кэша (\--cache-max-size), не кэшируется: ответ передается клиенту насквозь без сохранения в кэш.
  Запись кэша не должна удаляться механизмом освобождения памяти (аллокация нового сегмента / GC), пока её читают активные клиентские сессии.
  Обработка полей заголовка, управляющих кэшированием, таких, как Last-modified, Pragma no-cache, Cache-Control и др., не обязательна.

# Требования к прокси

## Ресурсы

Нагрузка на процессор должна быть минимальна (в разумных пределах), особенно в простое, когда нет клиентских подключений.

## Ограничения по количеству клиентских сессий

Прокси не должен иметь ограничений по количеству клиентских сессий, кроме количества дескрипторов открытых файлов и размера ограниченной очереди ожидания (см. п. 3).

## Исчерпание пула и очереди

Очередь ожидающих сессий должна быть ограниченного размера (backlog). При переполнении очереди прокси должен ответить клиенту 503 Service Unavailable с текстовым пояснением и закрыть соединение, а не молча зависать или падать.

Допускается создание двух потоков на каждое клиентское соединение: «клиентский» поток обрабатывает соединение с клиентом, «серверный» – с сервером. В случае пула потоков, допускается разделение пула на две части, серверных и клиентских потоков, исполняющих разный код. При такой реализации в случае передачи клиенту полной записи кэша, серверный поток можно не запускать.

Прокси не должен отправлять клиенту заголовки ответа раньше, чем получит статус и заголовки от сервера (или примет решение об ошибке).
Тело ответа должно передаваться клиенту как только был получен первый байт от сервера.

# Требования к процессу и сигналам

Прокси должен корректно обрабатывать сигналы SIGINT и SIGTERM
При получении сигнала на завершение прокси должен выполнить graceful shutdown: перестать принимать новые соединения, закрыть активные соединения, завершить все потоки и освободить всю выделенную память.
Каждый этап завершения должен быть виден по сообщениям в stdout/логе (например: "Received shutdown signal", "All connections closed", "All threads have finished", "Proxy finished").
